# Storage adapters

Schema version 6 adds one-use OAuth state and encrypted GitHub credentials on the same database connection and migration lock. State binds the local owner, workspace generation, browser nonce hash, App configuration and expected connection revision; valid consumption commits before code exchange. A newer flow, disconnect or save advances the revision and fences older callbacks and remote work. Numeric GitHub identity stays pinned across local disconnect, while credentials and pending state are purged. Workspace deletion purges the connection and pin. App imports recheck a matching active credential revision inside the existing source-save transaction. The domain encrypts tokens and PKCE verifiers with authenticated AES-256-GCM using the local server secret; the database adapter accepts opaque envelopes, never plaintext provider tokens. This remains trusted-machine server-secret storage rather than an OS credential vault.

Schema version 5 adds snapshot-paged investigation history. A durable `local_event_intakes` ordinal is allocated in the same transaction as each new event and pending job. Its `INTEGER PRIMARY KEY AUTOINCREMENT` avoids reusing committed intake IDs after deletion, as described in the [SQLite documentation](https://www.sqlite.org/autoinc.html). Migration backfills existing events once without changing event IDs, sequence, summaries or jobs. A persisted signing key authenticates opaque cursors bound to the user, workspace, repository, session and access generations. Page queries use a fixed intake watermark and sequence boundaries, recheck current access and return only summaries linked to the selected events. Default pages contain the latest 20 events, at most 50; older/newer navigation can traverse the entire accepted history. Later uploads, including delayed lower sequences, require a fresh snapshot. Derived summaries and session totals remain live. Deletion cascades to intake rows and access tombstones still fence every read.

Schema version 4 stores immutable versions of imported repository files and backfills existing active contexts once inside the migration transaction. A source ID binds the local repository and verified workspace/repository generations, GitHub full name, path, commit (which may be null), blob SHA, and SHA-256 of the stored redacted text. Repeating that exact snapshot reuses its ID and first-import timestamp; changed content, provenance, or verified scope generation creates another version. Null commits remain null and use a separate internal identity key, rather than an invented commit. Imported context and current file pointers change atomically with the source index. A scoped context sidecar also fences the raw context JSON: an authorized repository whose stored context belongs to a stale generation returns no current import until a new verified import occurs.

Only files present in the latest bounded import participate in repository-source FTS5 search. An omitted file is no longer a current captured snapshot; a partial import does not prove that GitHub deleted it. Historical source IDs remain readable while the owning local scope is active. Repository/workspace deletion purges all versions, current pointers and index rows; stale imports are denied by the same generation and activity checks.

Retention is bounded to 32 MiB of redacted file text and 2,000 immutable versions per repository, in addition to the 2 MiB import-context limit. Admission is checked before changing current pointers. Exceeding history capacity fails the whole import with `SOURCE_HISTORY_LIMIT` (HTTP 413), without evicting old citations or changing the previous searchable snapshot. Deleting repository history is an explicit user action.

Code citations refer to lines in the stored redacted snapshot, whose line count can differ from GitHub after redaction. Source reads default to line 1 and 100 lines, at most 200 lines per request, and never return more than 16 KiB or 16,000 characters. Out-of-range starts fail honestly. `hasBefore`/`hasAfter` describe line pagination; `excerptTruncated` specifically indicates the byte/character cap cut the selected range. A very long single line can therefore be truncated without a later line page. Current search returns one bounded match per file around its first matching word, at most 20 files. No remote GitHub line anchor is fabricated.

Schema version 3 adds a persisted manual `retryCount` to enrichment jobs. Protected job listing exposes only scoped, generation-current status summaries and safe error codes. Explicit retries apply only to terminal failed jobs, reset the current three-attempt budget, preserve the same source event and job IDs, and clear the previous lease token. Active/completed/stale/deleted work cannot be reset. Lease tokens also fence completions from a worker that belonged to an earlier retry budget.

The working local MVP uses `SqliteEvidenceStore` and Node's built-in `node:sqlite` API. The API explicitly creates `.memvora/server.sqlite` during bootstrap; imports do not open a database. The synchronous adapter is intended for bounded personal use on one machine. It is not a hosted multi-user database.

`resolveDataDir()` uses absolute `MEMVORA_DATA_DIR` or the project root's `.memvora`. `loadLocalToken({create:true})` is called only by API startup, creates a random 32-byte credential when needed, and honors a validated `MEMVORA_LOCAL_TOKEN` override. Clients read the existing credential; they must not create another identity. Keep `.memvora` private and ignored by version control. A local plaintext database is not encrypted storage.

Evidence and its pending enrichment job are written in one `BEGIN IMMEDIATE` transaction before exact UUID acknowledgement. Repeated IDs compare canonical payload digests. A changed payload or conflicting session sequence rejects the whole batch. Stored events are defensively redacted; retries compare the original payload digest without storing the original secret-bearing text.

Each read and write applies the server-derived local workspace scope. Repository and session tombstones/generations fence deletion. Event deletion cascades to summaries and jobs; imported repository context is also removed for repository/workspace deletion. A delayed worker rechecks its lease and workspace/repository/session generations in the final-write transaction. Deleted workspace rows persist and never silently bootstrap a replacement.

Lexical recall uses SQLite FTS5 with quoted literal query tokens, internal BM25 ranking, SQL scope predicates, and at most 20 returned memories. Insert/update/delete triggers maintain the index in the same transaction as memory changes. Schema version 2 backfills existing version-1 memories once; normal startup does not rescan them. FTS5 support is required; no silent table-scan fallback is used. This is lexical retrieval, not vector similarity or calibrated confidence. Session context returns the latest 100 recorded events and matching summaries in sequence order; counts still include all stored events.

Recall expands a matching event through a separate scoped sequence-range query, so old errors retain their actual neighboring attempts even outside the latest timeline window. Expansion is bounded to three sequences on either side and ten returned event summaries. A small explicit set of recent-investigation prompts can recover the latest ten recorded events when lexical search has no match. This fallback respects repository selections (including an empty selection) and does not turn arbitrary unanswered queries into recent context. Pending summaries use labeled raw observations.

The PostgreSQL `createDatabase()` factory and `schema.ts` remain a draft future adapter. No PostgreSQL migration has been generated or applied; its existence does not make the local pipeline PostgreSQL-ready. Move production deployment to reviewed relational ownership, migrations, hosted authentication, and the durable queue adapter as described in the architecture.
