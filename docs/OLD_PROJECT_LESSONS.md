# What to preserve and change from the old projects

This scratch build preserves useful product ideas, not old implementation bugs. Findings below came from source review and isolated fixtures with stubbed network/storage, not a production benchmark or a claim about the speed of a programming language.

Reviewed source snapshots:

- Application: [harshitgupta31415/nyc-trial](https://github.com/harshitgupta31415/nyc-trial/tree/7a97a927df33d33d3e2a6cc254d72dcad43ca2ef)
- CLI: [harshitgupta31415/memvora-cli](https://github.com/harshitgupta31415/memvora-cli/tree/a79e5c6b78810f449234e6f5b3c89072b6c8e651)

## Keep

- Local execution evidence with cwd, repository, time and exit metadata, plus offline delivery.
- Investigation/watch-session grouping to keep related attempts together.
- Repository metadata, commits, files, issues and PR context with provenance.
- Small read-oriented memory tools for coding assistants.
- Token hashing, expiry, revocation, audit metadata and rate limiting.

## Proof expected from the rebuild

Every corrected behavior should have a focused regression or integration check. Passing a test around a pure helper is not enough to establish end-to-end durability, authorization or Windows compatibility. Test actual adapters and transactions where those guarantees live. Keep the old repository links for design traceability; do not copy old credentials, accounts, test outcomes or unfinished integrations into the new build.
